# 告別 3 AM 警報噩夢？Anthropic SRE 工程師親揭 AI 在系統維運中的能力極限與實戰真相

## 引言與背景：AI 真的能完全接管 SRE 值班嗎？

「Claude 真的能自動修復所有系統故障嗎？SRE 值班輪調是不是已經全交給 AI 了？我們是不是像十多年前 SRE 經典書籍預言的那樣，把自己自動化到失業了？」

在 InfoQ 的演講中，Anthropic AI 可靠性（AI Reliability）團隊的工程師 Alex 開宗明義地針對這些常見疑問給出了答案。Alex 過去曾服務於 Google Cloud Compute Engine（GCE）的 Escalation SRE 梯隊——那是當事故嚴重到連一般 SRE 都需要後援時的最終防線；如今，他在 Anthropic 的職責則是「維持 Claude 的正常運作」。基於在第一線運用大語言模型（LLM）處理真實系統故障（Incident Response）的經驗，他的回答非常明確：「**沒有（No），AI 目前完全無法取代 SRE 手動值班。**」

為了證實這點，Alex 提出了一系列坦誠的客觀事實：
* **團隊持續擴充**：Alex 所屬的 Anthropic AI 可靠性團隊成立即將滿一週年，非但沒有因為 AI 而縮編，反而在倫敦、都柏林與美國等地大規模招募新成員，甚至包含 Staff 級別的高階職位。
* **AI 本身也會停機**：Claude 自身亦面臨故障與停機（Outages）。就在演講當天，系統才剛發生過事故，引發社群媒體上的熱烈討論與迷因。

針對當前風險投資（VC）熱情追捧 AI Ops 新創公司、各家紛紛推出預先包裝好的基準測試（Prepackaged Benchmarks）現象，Alex 保持高度審慎。市場上的展示往往基於結構完整、敘述乾淨的 Prompt，但這與凌晨 3 點突然響起、資訊極度混亂且零碎的真實故障警報有著本質上的巨大差異。AI 遠非萬能靈藥，但它在維運領域的確展現了獨特的價值。

## 為什麼我們依然期盼 AI SRE 成功？值班稅與職涯升遷的現實

儘管現狀尚未實現全自動化，Alex 依然強烈支持並期待 AI 在系統維運上的突破。他從工程師的現實處境出發，歸納出兩個核心原因：

* **值班的人性代價（On-call as a Tax）**：
  值班本質上是系統設計不夠完善而強加給工程師的「人性稅收」。警報聲會在半夜將人從深層睡眠中驚醒，剝奪睡眠、注意力以及與家人朋友相處的時間。Alex 坦言自己算是幸運的，團隊採用「順日輪調（Follow-the-Sun）」模式，倫敦團隊在晚上 6 點將值班交接給美國西岸，讓他還能去酒吧放鬆；最糟的情況頂多是早上 6 點起床。然而，許多工程師面臨的是 24/7 全天候輪調，凌晨 3 點被警報叫醒，剛睡著又在 4 點 30 分因為另一個資料庫故障被吵醒，到了早上 9 點還得準時參加 Daily Standup 保持專業形象。業界常將搶修過程包裝成英勇的「戰功故事（War Stories）」，但這種精神消耗對身心健康是不折不扣的損耗。若機能良好的 AI 能分擔這份沉重負擔，無疑是廣大工程師的福音。
* **職涯升遷的真相**：
  許多工程師以為成功搶救火災能帶來升遷，但資深工程師給出的職涯建議卻是：「**修復故障不會讓你獲得升遷。**」對初階工程師而言，修復生產環境問題是證明能力的訊號；但對 Senior 以上的工程師來說，搶修只是基本職責（Table Stakes）。真正能讓你展現影響力、晉升為 Tech Lead 的關鍵，是**建立能夠讓一整類故障「結構性地永遠不再發生」的機制與平台**。若 AI 能接管例行性的故障緩解（如標準 Rollback、例行處置），人類工程師才能騰出精力進行預防性的平台建設。

## OODA 循環下的 AI 表現：極度不均勻的「鋸齒狀（Jagged）」能力

為了精準剖析 LLM 在事故處理中的真實能力，Alex 引入了源自美國空軍上校、原本用於訓練戰鬥機飛行員的 **OODA 循環（Observe 觀察、Orient 定位、Decide 決策、Act 行動）** 框架。

在故障排除的生命週期中，LLM 展現出極度不均勻、呈「鋸齒狀（Jagged）」的能力分布：
1. **Observe（觀察）**：收集訊號、監控圖表與日誌。AI 在此階段具備超乎人類的速度與平行處理能力。
2. **Orient（定位）**：理解訊息意義，建立系統的心智模型。AI 在此階段極易混淆因果關係與相關性，充滿陷阱。
3. **Decide（決策）與 Act（行動）**：決定應對策略並執行指令。AI 的表現仍相當模稜兩可。

### 3.1 Observe（觀察階段）：超乎人類的超能力（Superhuman）

在收集訊號、檢索日誌與跨系統查詢上，LLM 展現出人類完全無法企及的速度與平行處理能力。它能精準撰寫 PromQL、以 IO 極速讀取幾千行日誌，且完全不會感到疲倦或分散注意力。

#### 實戰案例一：跨年夜 500 錯誤與欺詐帳號定位
在 12 月 31 日跨年夜，團隊維持最低限度人力時，Claude Opus 4.5 推論服務層顯示 500 HTTP 內部錯誤急劇上升。Alex 使用 Claude Code 進行排查。由於事先備有 `skill.md`（向模型說明請求生命週期：從邊緣伺服器、API 前端配額檢查、到推論後端 GPU/TPU 矩陣運算）與資料庫說明檔（說明資料倉庫主表結構與自我檢視方式），Claude 展現了驚人的分析能力：
1. Claude 自行編寫 SQL 查詢，秒級定位出錯誤來自圖片處理路徑中的未處理例外（Unhandled Exception）。
2. 在 Monorepo 中追蹤程式碼與 Git 變更，並分析失敗請求的原始 JSON Payload，發現引發 Bug 的請求均包含 **22 張圖片與一個 PDF 隨附檔案**。
3. Claude 自動擴大查詢範圍，發現同一時間有約 200 個帳號發送此特定 Payload，隨後更追查出同一時間區段內，有約 4,000 個採用相同郵件範本與郵件服務提供商創建的帳號（其中 3,800 個處於潛伏狀態），並以每分鐘 9 個帳號的速率註冊，成功揭露這是一起自動化帳號欺詐事件。

Alex 將此經驗稱為他的「**Move 37 時刻**」（比喻 AlphaGo 對決李世石時劃時代的一手）。若由人工排查，工程師只會將其標記為 API 團隊的 Bug，而不會在跨年夜跨權限通知帳號濫用（Account Abuse）團隊處理。

#### 實戰案例二：Pre-fill 伺服器 Rust Panic 快速定位
一位剛加入團隊 2 至 3 個月的成員，在面臨生產環境 Rust Panic 故障時，直接將日誌資料餵給 Claude Code 分析。Claude 在幾秒內便定位出 `checkpoint.rs` 中的 Segment ID 驗證錯誤、正確的文件行號與斷言訊息，並繪製出橫跨兩個獨立硬體平台的故障分佈圖。其訊號收集效率遠超正手動翻閱兩頁日誌的資深工程師。

### 3.2 Orient（定位階段）：混淆因果與相關性的致命陷阱

然而，一旦進入 Orient（定位與心智模型建立）階段，LLM 的表現便急轉直下。

#### KV Cache 運作機制與故障特徵
LLM 推論的核心機制包含兩個階段：
* **Prefill（預填階段）**：平行處理整個 Prompt 內容並生成 Key-Value 向量矩陣（KV Cache），屬於計算密集型（Compute-bound）。
* **Decode（解碼階段）**：利用儲存好的 KV Cache，逐字生成並 Streaming 輸出 Token。

當 KV Cache 因為系統問題失效或損毀時，伺服器必須重新對大量請求進行計算密集的 Prefill 處理。這會導致監控圖表呈現特定特徵：**請求量（Request Volume）與錯誤率（Error Rate）在同一個時間點同時暴增翻倍**。

#### Claude 的致命盲點：因果混淆
每一次看到這種「請求量與錯誤率同步暴增」的圖表，Claude 都會給出相同的錯誤結論：「請求量增加，這是容量問題，請增加更多伺服器。」

Claude 無法分辨「因果關係（Causation）」與「相關性（Correlation）」。它看到兩條線同時上升，就直接套用最常見的容量擴充模式，忽視了「快取失效導致重複計算」這一真正根因。若缺乏人類工程師積累的「疤痕組織（Scar Tissue，指過往慘痛故障經驗所形成的直覺）」，初階工程師極易被 AI 的錯誤定位誤導，採取無效甚至有害的應對措施（例如加開伺服器而非修復快取）。

## 自動化分級與 5 大落地實務模式（5 Working Patterns）

參照美國汽車工程師學會（SAE）對自動駕駛的 Level 0 至 Level 5 分級，SRE 維運自動化亦可映射為四個維度：**偵測（Detection）、初始回應（Initial Response）、預防（Prevention）、維運領域適應力（Operational Domain）**。目前業界正處於 Level 2 至 Level 3 的過渡期。

為了在現有技術限制下最大化 AI 效益，Anthropic 團隊經過一年的實踐，歸納出 **5 大落地實務模式**：

| 實務模式 | 運作機制與效益 | 注意事項 / 最佳實踐 |
| :--- | :--- | :--- |
| **1. 警報表達式直接交給 Async Agent** | 將 Infrastructure as Code 中的 PromQL/警報表達式直接傳給 Agent。在工程師開啟電腦前，Agent 已完成多維度下探（Pivot/Drill-down）。 | 設定好奇心指令，讓 Agent 自動比較上週流量、狀態碼與區域分布。 |
| **2. 單一 Trace ID 跨系統追蹤** | 指示 LLM 沿著 Trace ID 跨越不同雲端與日誌源，重構請求在各服務間的生命週期時間軸。 | 能快速釐清是 API 逾時還是後端推論逾時，並針對異常節點進行深度提問。 |
| **3. 變更時間軸比對（What Changed Window）** | 將故障時間窗口提供給 LLM，對照公司內部的部署記錄、設定變更與 Feature Flags。 | 須防止 AI 過度興奮而斷言根因；應將其定位為「潛在懷疑清單」，若 Rollback 成本低可優先嘗試。 |
| **4. 檢討報告（Post-mortems）初稿自動化** | 過去檢討報告常被當成指派給初中階工程師的繁重雜務（「參與事故的獎勵」）。現在可將 Slack 頻道紀錄與會議逐字稿餵給 LLM 生成 80% 初稿。 | **必須加入強制指令**：「對不確定的事項插入 `TODO for human`」。避免未審核的虛假內容散播；若直接將未經審核的報告餵回 LLM，會造成未來規劃上的「垃圾進，垃圾出（Garbage In, Garbage Out）」惡性循環。 |
| **5. 交班摘要（Shift Handoffs）** | 要求團隊「在公共頻道思考（Build in Public）」，將除錯過程寫在頻道中。在倫敦日間班次積累 200 至 400 條訊息後，由 Claude 濃縮為精準摘要。 | 極低風險且效果顯著，接班工程師只需閱讀帶連結的一段摘要即可快速掌握狀況。 |

## 未來隱憂：技能退化、Jevons 悖論與 METR 自主成長

隨著 AI 深度參與維運，技術團隊將面臨更深層次的組織與技術挑戰。

### 技能退化風險（Skill Atrophy）
資深故障排除者的直覺來自於過去被系統「燙傷」的經驗。如果 AI 接管了從發現問題到建議處置的全過程，工程師將喪失關鍵的反饋循環：
* **資深工程師**：缺乏實際操作的反饋，可能導致處置直覺與疤痕組織退化。
* **初階工程師**：失去在簡單事故中磨練指令操作與排查邏輯的機會。當出現 AI 無法處理的複雜系統故障時，人類團隊可能陷入無法有效回應的困境。

### Jevons 悖論（Jevons Paradox）在軟體領域的展現
引用 OpenAI 研究員 Rune 的觀點，Jevons 悖論指出：**當技術進步提高了資源使用效率、降低使用成本時，資源的總消耗量反而會劇烈增加，而非減少。**

在 AI 輔助開發的背景下：
1. 撰寫程式碼與開發軟體的效率大幅提升、成本下降。
2. 軟體產出的數量與系統複雜度呈現爆炸性成長。
3. 複雜度的劇增引發更詭譎、更難預測的故障模式。
4. 最終導致維運需求與值班負擔不減反增。

### METR 數據與終極思考
模型評估機構 METR 的研究圖表顯示，AI 模型能夠自主執行任務的時間跨度呈指數級增長（Scaling Laws 依然生效）。

這引發了一個終極思考：AI Agent 未來是否能消耗無上限的計算資源，來主動簡化與管理人類所建立的日益複雜的系統？抑或人類將被困在複雜度暴增的循環之中？這仍是尚未有確定答案的議題。

## 結論與 Key Takeaways

AI 不是替代 SRE 工程師的萬靈丹，而是一個具備「超人類級別觀察力」、但在「因果定位上極易犯錯」的高效助手。成功運用 AI Ops 的關鍵，在於明確劃分人類與 AI 的權責邊界，利用 AI 減輕例行性負擔，讓工程師能回歸結構性預防的本業。

以下是實踐 AI SRE 的 4 大核心啟示：

* **定位 AI 角色**：將 AI 聚焦於 **Observe（訊號收集與數據擷取）**，絕不盲目信任其在 **Orient（因果判斷與根因分析）** 的結論。
* **優化 Context & Prompt 結構**：透過建立 `skill.md` 與清晰的系統架構說明文檔，提供模型充足的上下文資訊，大幅提升排查精準度。
* **建立安全機制**：在自動化產出（特別是 Post-mortem 檢討報告）中，強制實施 `TODO for human` 審核機制，防止未經證實的資訊污染知識庫，避免「垃圾進，垃圾出」。
* **專注結構性預防**：善用 AI 簡化例行故障緩解的特性，將省下的人力與時間，投注於「徹底消除同類故障」的平台架構建設上。
