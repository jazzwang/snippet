# 3.5GB 模型真能取代 21GB 的日常主力？Bonsai 27B 深度實測解析

## 1. 引言：小模型挑戰大模型的「不可能任務」

在 AI 硬體效能的世界裡，我們通常遵循一個鐵律：體積越大，智力越高。但今天，一個僅有 **3.5GB** 的模型竟然宣稱能完成與 **21GB** 日常主力模型 (Qwen 35B MoE) 相同的工作，這引起了我的強烈好奇。

本次測試的核心問題在於：當模型體積被極端壓縮，其「智力密度」(Intelligence Density) 是否依然足以支撐專業任務？對我個人而言，這場實測更有其必要性——因為我的測試硬體（RTX 3060）根本無法跑動原始體積超過 50GB 的 27B 密集型模型，而這正是 **Bonsai 27B** 的由來。

**Bonsai 系列模型的特殊之處在於，它不是訓練後才進行「量化」縮減，而是從訓練的第一天起，就以 1-bit 或 1.5-bit 的「量化訓練」(Quantization Aware Training, QAT) 打造而成。** 權重中甚至沒有小數點，這種從底層邏輯重構的技術，究竟是行銷術語，還是邊緣運算的未來？

---

## 2. 技術解密：Bonsai 模型為什麼與眾不同？

傳統的 Q4 量化是將已訓練好的 16-bit 模型強行截斷小數點，這往往會造成智力損失。但 Bonsai（推測採用了類 BitNet 架構）在訓練過程中就讓模型適應了極簡的權重表現：

*   **Binary (二進制) 版本**：僅 3.5GB，權重非黑即白，只有 -1 或 +1。
*   **Ternary (三進制) 版本**：約 7GB，權重包含 -1、0 或 +1。

官方宣稱這種訓練方式能保留原始品質的 90-95%。目前，Ternary 版本已能在 Apple Silicon (Metal 支援已併入 llama.cpp) 與手機上流暢運行，這讓 Mac 用戶在本地運行大模型的體驗上難得領先了一回。

## 3. 實測第一戰：前端 UI 設計能力

我們要求模型一鍵生成一個包含 CSS 的單一 HTML 網頁，並設定嚴格禁令：**禁止任何外部請求 (No CDN/External links)**。這迫使模型必須具備編寫原生 CSS 的能力，而非背誦 Tailwind 等框架的類別名稱。

| 模型名稱 | 體積 | 設計表現評等 | 關鍵評論 |
| :--- | :--- | :--- | :--- |
| Qwen 35B MoE | 21GB | 優異 (靠近基準線) | 佈局具備深度感與考究的間距，最接近雲端旗艦模型。 |
| Bonsai Ternary | 7GB | 優異 | 視覺上與 21GB 模型難以區別，但在長文件結尾的 SVG 座標處理上會停頓。 |
| Bonsai Binary | 3.5GB | 良好但有瑕疵 | 出現佈局衝突，例如終端機圖形元件會遮蓋標題文字。 |
| Gemma 12B | 7GB | 普通 | 作為對照組，產出的文件僅 12KB，內容極其單薄，像被放棄的模板。 |

**筆記：** 實測中，我驚訝地發現從遠處看，Bonsai Ternary 與 Qwen 35B 生成的深色模式網頁幾乎難分高下。

## 4. 實測第二戰：伺服器故障診斷與修復

### 初級測試：磁碟空間清理
在基本的故障排除中，所有模型都精準定位了佔用空間的日誌檔。但在誠實度上出現分歧：**Binary 版本**在confused時會「寫小說」，宣稱清除了 100MB（實則為 1.45GB）；反觀 **Gemma 12B** 則會主動進行算術校驗以確保數據精準。

### 進階測試：三層跳轉修復
這是一個包含 Gateway 配置錯誤、設定檔模板覆蓋機制以及惡意日誌誘餌的複雜環境。

*   **Bonsai Ternary (7GB)**：表現驚豔，它產出了我見過最聰明的診斷動作——當它發現某個連接埠回傳正常時，它沒有直接放棄，而是主動執行 `curl` 驗證不同連接埠的連通性。它是在做「實驗」，而非僅依賴書面文件。
*   **Bonsai Binary (3.5GB)**：雖然最終解決了問題，但過程充滿「混亂」。它在修復過程中曾誤刪文件，甚至試圖對核心系統進程執行 `kill -9`，所幸沙盒權限阻止了這場災難。
*   **Gemma 12B 的徹底失敗**：即使調整了 Temperature (溫度) 與重複懲罰，Gemma 仍陷入無限決策循環，不斷執行相同指令卻無法推進任務。

**效率對比：** 在這項任務中，21GB 的模型在 1 分鐘內完賽，而 3.5GB 模型則花了超過 2 分鐘。

## 5. 速度與架構的弔詭：為何大模型反而更快？

在我的測試中，21GB 的 Qwen 每秒產出 48 個 Token，而 7GB 的 Bonsai Ternary 僅有 22 個。這看似不合理，但技術核心就在於：

> **「量化縮小的是文件，MoE 縮小的是數學。」**

*   **Qwen 35B MoE**：雖然體積大，但採用「專家混合」架構，每代幣僅激活 **3B 參數**。計算負擔輕，所以速度極快。
*   **Bonsai 27B**：屬於「密集型」(Dense) 架構，雖然權重文件被壓縮，但每代幣仍需運算全量 **27B 參數**。

簡單來說，Bonsai 是讓 GPU 搬運較輕的數據，但進行極其沉重的計算；而 MoE 則是搬運沉重的數據，但計算卻非常輕量。

## 6. 硬體適配指南：你該選擇哪一個？

模型選擇不應只看參數，更要看你的「智力每 GB」(Intelligence per Gigabyte) 需求：

*   [ ] **擁有 12GB 以上顯卡 + 充足系統記憶體：**
    首選 **Qwen 35B MoE**。速度是王道，且長文本穩定性（不晃動、不重複）依然是目前最強。
*   [ ] **Apple Silicon (Mac) 用戶：**
    首選 **Bonsai Ternary (7GB)**。由於 Mac 採用統一記憶體 (Unified Memory)，無法像 PC 一樣透過分層存儲 (Offloading) 來優化 MoE，這使得體積小、智力密度高的 Bonsai 成為最佳平衡點。
*   [ ] **6-8GB 顯卡或舊型個人電腦：**
    選擇 **Bonsai Binary (3.5GB)**。這是目前市面上唯一能讓低 VRAM 顯卡跑動「27B 智力等級」的模型，雖然路徑混亂且長文件易出錯，但解決複雜問題的能力遠超同體積模型。

---

## 7. 結論：1-bit AI 的未來展望

Bonsai 的實測向我們證明了「智力密度」的巨大潛力。雖然目前在處理速度上仍輸給 MoE 架構，且在長文本穩定性上存在弱點，但它成功將原本需要 50GB VRAM 的智力等級，塞進了一個隨身碟大小的空間中。

展望未來，我最期待的是 **MoE (縮減計算量)** 與 **Ternary (縮減文件體積)** 技術的融合。想像一個 250B 參數等級的模型，透過這兩種技術優化後，可能只需 20GB 的下載空間即可在消費級顯卡上運行。

**最後一個問題留給各位：在有限的記憶體面前，你會選擇「體積大但算得快」的 MoE 模型，還是「體積極小但算得深」的高密度壓縮模型？歡迎在留言區分享你的選擇。**
