### Google 開放知識格式 (OKF)：重新定義 AI 記憶架構與資料管理

#### 執行摘要

長期以來，人工智慧產業普遍採用「檢索增強生成」（RAG）技術，透過將文件切割、轉化為向量並儲存於專用資料庫中，來為模型提供外部記憶。然而，AI 領域的權威人士 Andrej Karpathy 與 Google 提出了一種顛覆性的替代方案：**開放知識格式 (Open Knowledge Format, OKF)**。

OKF 的核心理念是棄繁就簡，主張利用結構化的純文字資料夾（如 Markdown 檔案）來取代複雜的向量資料庫。這種方式將「LLM 維基」視為程式碼庫，由 AI 擔任維護者與程式設計師。Google 於 2024 年 6 月將此概念正式規範化，旨在解決 RAG 每次查詢都需重新運算、難以管理及不具透明度的痛點。儘管此格式在可讀性、擴展性與 Git 整合方面具有顯著優勢，但其在維護機制、AI 寫作準確性以及語義標準化方面仍面臨挑戰。

#### 核心主題分析

##### 1. 從 RAG 到 LLM 維基：記憶架構的範式轉移

傳統的 RAG 模式存在效率瓶頸：

*   **重現負擔：** 每次查詢都是從零開始，模型必須在成千上萬的片段中重新建立邏輯關聯，即使是相同的問題，運算成本依然高昂。
*   **結構散亂：** 企業數據散落在資料庫、管線、拉取請求 (Pull Requests) 以及工程師的腦海中，RAG 僅是將這些碎片強行湊合。

**OKF/LLM 維基的逆向思維：**

與其在提問時才進行運算，不如預先將知識建構成一個相互連結的文字檔案資料夾。這就像是為模型編寫一本「百科全書」，讓 AI 像開發者閱讀程式碼庫一樣閱讀這些檔案。

##### 2. Google OKF 規範詳解

Google Cloud 發布的 OKF 規範極其簡約，其主要特徵如下：

| 組成元素 | 描述 |
| --- | --- |
| **Bundle (軟體包)** | 一個資料夾。 |
| **檔案結構** | 每個檔案代表一個單一概念（如：指標定義、劇本、表格）。 |
| **命名與連結** | 檔案路徑即為其名稱，檔案間的連結構成知識圖譜。 |
| **特殊檔案** | 包含目錄列表檔案與變更日誌檔案。 |
| **硬性規定** | 每個檔案必須有一個欄位標註其「類型」(Type)。 |
| **容錯機制** | 規範要求讀取工具必須忽略未知欄位、損壞的連結或無法解析的檔案（寬容模式）。 |

##### 3. OKF 的三大核心優勢

*   **預先運算 (Upfront Computation)：** 在構建 Bundle 時，AI 已經完成了連結概念、標註矛盾與撰寫摘要的工作。使用者提問時，僅需讀取成品，無需重複支付理解成本。
*   **卓越的擴展性 (Scale)：** 透過短小的目錄檔案，模型能快速篩選出所需的檔案（例如從 9,000 個檔案中選出 1 個），避免了長文本處理的負荷與窒息感。
*   **純文字與在地化 (Text-Only)：** 由於本質是文字，它可以儲存在 Git 中進行版本控制、代碼審查，甚至能在離線筆記本電腦上運行，無需 API 金鑰或複雜的資料庫伺服器。

##### 4. 關鍵挑戰與局限性

*   **維護與過時風險：** 規範本身缺乏自動更新機制。在團隊協作環境下，若無人維護，資料夾內容可能在一個月內就會過時，導致 AI 給出錯誤的陳舊資訊。
*   **AI 檔案管理的精準度：** 語言模型在撰寫乾淨的 Markdown 格式方面表現並不穩定，常會出現損壞的標題或指向不存在檔案的連結。Google 的應對方式是採取「寬容讀取」，而非修復寫作問題。
*   **語義一致性問題：** 雖然規範了容器格式，但未規範內容意義。例如，不同團隊可能將相同的內容標註為 `BigQuery table`、`Table` 或 `Relational Asset`，這種自由格式標籤會導致溝通障礙。

##### 重要語錄與背景分析

> **「Obsidian 是整合開發環境 (IDE)，LLM 是程式設計師，維基是程式碼庫。資料夾是你擁有的部分，模型則是負責維護它的員工。」**
> — *摘錄自 Andrej Karpathy 的概念描述*

**背景：** 這段話定義了人類、模型與數據之間的新型關係。人類提供素材，AI 負責總結、交叉引用與歸檔，打破了人類必須手動維護筆記的迷思。

> **「代理程式 (Agent) 基本上就是一個 Markdown 檔案資料夾。」**
> — *摘錄自開發者評論*

**背景：** 簡化了 AI Agent 的本質。這強調了競爭優勢不在於複雜的基礎設施，而在於資料夾如何組織、哪些內容被鎖定、以及如何防止內容隨著時間推移而產生偏誤（Drifting）。

> **「一個只有一個使用者的標準，僅僅是一個建議。」**
> — *摘錄自關於 OKF 普及率的評論*

**背景：** 指出 Google OKF 目前的市場地位。儘管概念領先，但目前主要與 Google 自身的產品（如 BigQuery、Gemini、NotebookLM）深度綁定，尚未獲得廣泛的外部採納。

#### 洞察與建議

1.  **優先考慮簡單性：** 企業應評估是否真的需要昂貴且複雜的向量資料庫。對於許多私有知識管理情境，結構化的文字資料夾可能更高效且易於審查。
2.  **建立內部語義規範：** 由於 OKF 的類型欄位是自由格式，企業在使用時必須制定內部的「命名標籤標準」，以確保不同團隊產出的 Bundle 能夠互通。
3.  **解決「維護 rot (腐爛)」：** OKF 的成功取決於 AI 能否持續更新內容。應建立明確的流程或使用特定的 AI 代理程式定期掃描並修正過時資訊，而非單純依賴格式規範。
4.  **善用 Git 流程：** 將 AI 生成的知識納入 Git 工作流。利用 Pull Requests 讓人類專家審查 AI 撰寫的維基，這是 RAG 模式難以實現的透明度與準確度保障。
5.  **觀察 Google 的生態布局：** OKF 與 BigQuery 和 Gemini 的深度整合顯示，Google 試圖透過格式標準化，將企業數據更順暢地導入其 AI 生態系統。企業在採用時應考量供應商鎖定的風險。
